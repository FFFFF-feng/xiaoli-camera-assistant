# 小栗摄影助手参赛材料设计草案

本作品面向赛题4“AI+场景创新”，定位为帮助摄影新手在现场理解取景与设备设置的辅助工具，而不是通用聊天机器人或自动生成摄影成片的工具。核心展示应回答：用户面对一个具体场景，如何从“不知道怎样拍”，走到“知道下一步可以怎样调整”。

本草案依据团队提供的提交规范编排。正式作品方案仍需套用赛事官方模板；当前未读取到网盘模板，以下章节不是官方大纲。团队编号、截止时间、模板栏目及报名系统限制须在提交前核对。

## 作品名称与简介

建议作品名称：小栗摄影助手。

建议副标题：面向摄影新手的场景理解与可视化构图指导。副标题用于封面说明，不与作品名称字段合并，以免超过20字。

建议作品简介如下，可直接作为报名字段初稿：

摄影新手常常知道想拍什么，却不知道如何取景、选择焦段和设置设备。小栗摄影助手结合现场原图、拍摄目标与器材信息，通过多模态场景分析和分库知识检索，提供保留可见物体轮廓与环境关系的构图线稿、三分线参照及拍摄步骤。用户可对照原图理解主体大小、位置和取景范围，并参考适配设备的参数建议进行试拍。项目提供网页端、Android演示客户端及知识导入工作台，面向日常摄影、校园摄影与入门教学，探索将抽象摄影知识转化为可理解、可尝试的现场指导。

简介中的效果是“可对照、可理解、可试拍”，不写尚未测量的准确率、提升比例或市场收益。

## 参赛叙事与核心场景

主场景选校园或公园的一处普通景物，包含清晰主体和一定背景，例如花朵与枝叶、建筑与树木、人物与环境。优先使用团队自摄且有权展示的照片。一个案例贯穿需求、分析、线稿、参数、试拍；另外两类案例放入作品方案及答辩备份页，证明适用范围，而不是在主视频里频繁切换。

叙事顺序为：新手的具体困惑、现场输入、设备条件、可视化指导、执行动作、实际验证、应用价值。不要以登录连接、后台配置或项目文件列表开场。技术解释紧随对应结果，让评委看到技术为什么需要，而不是先听术语。

作品的主要价值主张是“解释如何拍”，不是“替用户拍”。构图图是建议示意，物体识别、边界表达和知识检索都可能有误差；建议通过原图对照、来源与现场试拍核对。

## 创新点及对应证据

以下是本项目的设计特色，不等同于已证明的行业首创。每个特色至少配一项可复核的界面或实验材料。

| 设计特色 | 要展示的实际内容 | 证明方式与边界 |
| --- | --- | --- |
| 将摄影建议转为可视化构图参照 | 原图、保留可见轮廓和环境的线稿、主体相对大小和位置、三分线 | 展示同一输入对应的结果，不把线稿当成真实新机位照片 |
| 将用户目标与器材条件一起纳入建议 | 同一场景的目标输入，已收录设备及镜头选择，报告中的设置理由 | 未核验能力不自动推断；设备目录数量不等于完整能力覆盖 |
| 让知识内容可管理和追溯 | 分库导入、格式预览、版本及审核状态，报告中实际命中的来源 | 上传通过不代表知识正确或已发布；未命中时不能编造依据 |
| 提供从理解到行动的使用流程 | 线稿解释、现场步骤、本机结果回看 | 实际改善需试拍验证；实时取景指导仍为后续方向 |

| 应用可行性 | 校园摄影、新手教学等场景如何落地 | 拟试点流程、成本构成、潜在合作方式 |

实际技术流程可表述为：原图和需求输入 → 图片与设备信息检查 → 场景结构分析与相关资料检索 → 构图及拍摄建议 → 轮廓和环境示意 → 原图对照与现场试拍。具体并行顺序和检索算法以代码为准，不把向量召回、重排或实时控制写成默认已实现。

默认轮廓路线使用CPU GrabCut；MobileSAM属于显式配置的可选后端，图片编辑服务也不是默认必需项。模型识别与建议生成依赖后端及配置的模型服务，不能称为手机完全离线推理。

## 四分三十秒演示视频设计

主视频目标时长4分30秒，保留剪辑余量。详细操作和逐段口播见同目录的 `competition-demo-20261019.md`。视频不展示安装、密钥、登录和漫长连接配置，直接从一个已经准备好的真实拍摄问题进入。

| 时间 | 画面 | 目的 |
| --- | --- | --- |
| 00:00—00:25 | 项目名称、现场原图和新手困惑 | 让评委理解场景与痛点 |
| 00:25—01:00 | 上传原图、输入目标、选择实际设备 | 交代输入和使用方式 |
| 01:00—01:20 | 本次真实分析进度与简洁流程说明 | 解释系统如何处理，不用术语堆叠 |
| 01:20—02:30 | 原图与线稿、轮廓和环境、三分线及填色 | 集中展示构图反馈这一核心特色 |
| 02:30—03:05 | 参数理由与现场步骤 | 把图形建议变成拍摄动作 |
| 03:05—03:30 | 真实试拍对照或清楚标注的建议解读 | 证明可执行性，区分示意与实拍 |
| 03:30—03:55 | 实际命中的来源和知识工作台短镜头 | 交代知识维护与可追溯性 |
| 03:55—04:15 | 已有验证与限制 | 展示工程可信度，不虚报效果 |
| 04:15—04:30 | 应用场景与下一阶段 | 收束价值与路线 |

视频必须为MP4，严格处于3至5分钟且小于300 MB。建议1080p、H.264视频加AAC音频，作为兼容性选择而非赛事额外规定。4分30秒按视频5 Mbps和音频128 kbps估算约173 MB，仍需检查最终文件的实际大小和时长；建议控制在250 MB以内留余量。等待过程可以剪辑或加速，但需明确标注，不能把剪辑后的间隔当成推理耗时。

## 验证与佐证材料准备

当前应先解决“本地网页提交照片分析失败”并完成一次真实模式的完整流程验证，再录制主案例。APK可构建、签名有效与前端测试通过，不能替代真机安装、权限、上传及报告展示验收。

建议建立一个小规模可复核验证集，例如12个自摄场景，覆盖人物、静物、建筑、自然景观，每类3个；再邀请5位新手体验。该规模仅为团队执行建议，不是赛事要求，也不是已有实验结果。保留失败样本，不只选最好看的案例。

| 验证问题 | 记录方法 | 提交时如何表述 |
| --- | --- | --- |
| 是否能完成分析 | 固定版本和模式，记录有效提交次数、完整报告次数与错误 | 以完整报告数除以有效提交数；说明失败和测试条件 |
| 等待是否可接受 | 记录未剪辑的提交及完成时间 | 给出样本量、中位耗时与范围，不只报最快一次 |
| 轮廓是否保留主体与环境 | 两名成员独立核对主体可辨性、相对大小、位置和环境保留 | 分项报告一致与分歧，不把主观评分称为通用准确率 |
| 是否出现不可执行的建议 | 逐条核对设备能力、物体关系、参数依据与现场动作 | 单列错误及未知项，不用“100%匹配”概括 |
| 可视化是否更易理解 | 同场景比较文字版与图文版，交错展示顺序，记录理解时间和可执行动作 | 说明样本小、顺序及偏差，不声称已获统计显著提升 |
| 试拍是否体现目标 | 相近时间、相同设备与模式下保留原始试拍和调整后照片 | 区分构图变化与光照、曝光或后期变化 |

佐证PDF可收录版本与构建记录、真实功能测试、授权的自摄输入输出、原始试拍、匿名反馈、团队分工、开源依赖及许可说明。它们用于支持作品真实性和过程可追溯，不保证等同于主办方认可的专利、软著或正式应用证明。没有的证书和合作不得伪造；优先按报名系统列出的认可类别提交。

反馈前告知参与者用途，取得照片及反馈使用许可。原始照片、定位信息、人脸、令牌和模型密钥不能未经处理出现在公开材料中。开源代码引用、设备数据来源及图片授权单独列出，保留必要署名。

## 三人推进与交付顺序
